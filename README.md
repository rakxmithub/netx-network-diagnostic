## 🧠 About

<div align="center">
<img src="https://readme-typing-svg.demolab.com?font=JetBrains+Mono&weight=600&size=15&duration=1800&pause=600&color=00FF88&center=true&vCenter=true&width=950&height=40&lines=One+tool.+Every+network+answer.;Designed+for+speed%2C+clarity+and+control.;No+GUI.+No+clutter.+Just+signal." alt="about animation"/>
</div>

**NetX** is a Python-based network diagnostic and monitoring toolkit built for Windows. It merges every essential networking utility — Wi‑Fi analysis, DNS benchmarking, ping monitoring, traceroute, connection-drop detection, and full system health scoring — into a single, fast, terminal-native application.

Instead of juggling `cmd`, `Resource Monitor`, third-party Wi‑Fi analyzers, and a DNS speed tester, NetX wraps native Windows tools (`netsh`, `ipconfig`, `ping`, `tracert`) and Python's `socket` layer behind one clean, color-coded CLI. One binary. One menu. Every answer.

<div align="center">

| 💡 Built for | 🎯 Solves |
|:---|:---|
| Sysadmins & network engineers | *"Is it my Wi-Fi or my ISP?"* |
| Developers debugging latency | *"Why is my API suddenly slow?"* |
| Power users & tinkerers | *"What's actually on my network?"* |
| Support & helpdesk teams | *"Give me a report I can attach to a ticket."* |
| Remote workers | *"Is my connection stable enough for this call?"* |
| Students learning networking | *"What do these networking concepts look like in practice?"* |

</div>

## 🛠️ Configuration

NetX can optionally be tuned through a config file so you don't have to re-enter the same settings every run.

```yaml
# netx.config.yaml — place in project root

ping:
  target: 8.8.8.8
  count: 10
  timeout_ms: 1000

dns:
  resolvers:
    - name: Cloudflare
      ip: 1.1.1.1
    - name: Google
      ip: 8.8.8.8
    - name: Microsoft
      ip: 4.2.2.2
  test_domains:
    - google.com
    - github.com
    - cloudflare.com

monitor:
  interval_seconds: 1
  alert_threshold_ms: 80

report:
  output_dir: ./reports
  format: json
```

<div align="center">

| Setting | Default | Purpose |
|:---|:---|:---|
| `ping.target` | `8.8.8.8` | Host used for latency/packet-loss tests |
| `ping.count` | `10` | Number of ping packets sent per test |
| `dns.resolvers` | Cloudflare, Google, Microsoft | Resolvers included in the DNS benchmark |
| `monitor.interval_seconds` | `1` | Polling frequency for live monitors |
| `monitor.alert_threshold_ms` | `80` | Latency spike threshold before a `⚠` warning |
| `report.output_dir` | `.` (current dir) | Where JSON reports are written |

</div>

```text
                         │   report.py       │
                         │ (JSON Exporter)   │
                         └──────────────────┘
```

### Data Flow

```yaml
1. User selects a module from the CLI menu
2. Module shells out to the relevant native tool (netsh / ipconfig / ping / tracert)
   or opens a raw socket connection
3. Raw output is parsed into structured Python objects
4. Results are formatted with color-coded status markers
5. (Optional) health.py aggregates results into a 0–100 score
6. (Optional) report.py serializes results to timestamped JSON
```

## 📚 Module Deep Dive

<details>
<summary><b>📡 01 · Network Information</b></summary>
<br>

Reads local adapter configuration directly from `ipconfig /all` and parses it into structured fields.

```yaml
Reports:
  - IPv4 address, subnet mask, default gateway
  - MAC address per adapter
  - DNS servers in use
  - Connected Wi-Fi SSID, signal strength, and radio type
```

```bash
python main.py --module network-info
```

</details>

<details>
<summary><b>📶 02 · Ping Analysis</b></summary>
<br>

Sends a configurable burst of ICMP echo requests and computes latency statistics.

```yaml
Reports:
  - Minimum / Maximum / Average round-trip time
  - Packet loss percentage
  - Jitter (variance between consecutive pings)
  - A letter-style connection quality grade (Excellent → Poor)
```

```bash
python main.py --module ping
```

</details>

<details>
<summary><b>🌐 03 · Internet Test</b></summary>
<br>

Checks reachability at three layers — gateway, public DNS resolvers, and general internet — to isolate exactly where a connectivity issue lives.

```yaml
Checks:
  - Default gateway reachability
  - Cloudflare (1.1.1.1) reachability
  - Google DNS (8.8.8.8) reachability
  - Consolidated connectivity verdict
```

</details>

<details>
<summary><b>🔎 04 · DNS Test</b></summary>
<br>

Resolves a list of well-known domains and measures resolution time and success rate.

```yaml
Reports:
  - Per-domain resolution success/failure
  - Response time in milliseconds
  - Fastest-responding domain
```

</details>

<details>
<summary><b>⚡ 05 · DNS Benchmark</b></summary>
<br>

Compares multiple public DNS resolvers head-to-head and ranks them by response time.

```text
CLOUDFLARE   ████████████       18ms
GOOGLE       ███████████████    24ms
MICROSOFT    ██████████████████ 31ms
─────────────────────────────────────
🏆 FASTEST → CLOUDFLARE
```

Resolvers are configurable via `netx.config.yaml` under `dns.resolvers`.

</details>

<details>
<summary><b>📂 06 · Wi-Fi Profiles</b></summary>
<br>

Lists saved Wi-Fi profiles on the system via `netsh wlan show profiles`, with the option to reveal stored keys (local machine only — nothing leaves your device).

```yaml
Reports:
  - Saved SSID list
  - Authentication & encryption type
  - Stored password (requires Administrator)
  - Export to a local file
```

</details>

<details>
<summary><b>📡 07 · Wi-Fi Scanner</b></summary>
<br>

Scans for nearby wireless networks and ranks them by signal strength.

```yaml
Reports:
  - SSID and BSSID
  - Signal strength (bars + percentage)
  - Security type (Open / WPA2 / WPA3)
  - Channel, sorted by signal quality
```

</details>

<details>
<summary><b>📈 08 · Live Ping Monitor</b></summary>
<br>

Streams ping results in real time with inline spike and timeout flags.

```text
21:42:01  [✓]  31 ms
21:42:02  [✓]  34 ms
21:42:03  [✓]  36 ms
21:42:04  [!]  91 ms   ⚠ spike
21:42:05  [X]  TIMEOUT
21:42:06  [✓]  39 ms
```

Spike threshold is configurable via `monitor.alert_threshold_ms`.

</details>

<details>
<summary><b>📊 09 · Real-Time Network Monitor</b></summary>
<br>

A continuously refreshing dashboard summarizing current connection status.

```yaml
STATUS       : ONLINE
LATENCY      : 34 ms
PACKET LOSS  : 0%
STABILITY    : EXCELLENT
```

</details>

<details>
<summary><b>🚨 10 · Connection Drop Detector</b></summary>
<br>

Watches the connection continuously and timestamps every drop and recovery event — useful for building an evidence log for ISP support tickets.

```text
21:15:01  CONNECTION OK
21:15:02  CONNECTION OK
21:15:03  CONNECTION LOST      ⚠
21:15:04  CONNECTION LOST      ⚠
21:15:05  CONNECTION RESTORED  ✓
```

</details>

<details>
<summary><b>🧭 11 · Traceroute</b></summary>
<br>

Wraps `tracert` and renders the hop-by-hop path to a destination with per-hop latency.

```text
LOCAL ─► HOP 01 ─► HOP 02 ─► HOP 03 ─► DEST
  1ms      8ms       14ms      22ms    31ms
```

</details>

<details>
<summary><b>❤️ 12 · Network Health Score</b></summary>
<br>

Aggregates Wi-Fi status, gateway reachability, internet connectivity, DNS resolution, latency, and packet loss into a single 0–100 score with a letter-style verdict.

```text
Wi-Fi        [ OK ]      Latency   [ GOOD ]
Gateway      [ OK ]      Loss      [ 0%   ]
Internet     [ OK ]      DNS       [ OK   ]
──────────────────────────────────────────
        SCORE: 95 / 100  ★ EXCELLENT
```

</details>

<details>
<summary><b>🧠 13 · Full Diagnosis</b></summary>
<br>

Runs every check in sequence and prints a single pass/fail diagnosis — the fastest path from "something feels off" to a clear answer.

```yaml
> CHECKING WI-FI ............ OK
> CHECKING GATEWAY .......... OK
> CHECKING INTERNET ......... OK
> CHECKING DNS .............. OK
> CHECKING LATENCY .......... OK
> CHECKING PACKET LOSS ...... OK

```

</details>

<details>
<summary><b>💻 14 · System Information</b></summary>
<br>

Collects host-level context that's often relevant when troubleshooting network issues.

```yaml
Reports:
  - Hostname, OS version, architecture
  - CPU and RAM summary
  - Network adapter details (driver, speed, status)
```

</details>

<details>
<summary><b>💾 15 · JSON Export</b></summary>
<br>

Serializes the results of any module (or the full diagnosis) into a timestamped JSON report for archiving or attaching to support tickets.

## ❓ FAQ

<details>
<summary><b>💬 Does NetX need Administrator privileges?</b></summary>
<br>
Some modules — Wi-Fi profile passwords, certain adapter details — require running the terminal as Administrator on Windows. Most read-only diagnostics work without elevation.
</details>

<details>
<summary><b>💬 Does NetX work on Linux or macOS?</b></summary>
<br>
Not yet. NetX currently relies on Windows-native tools (<code>netsh</code>, <code>ipconfig</code>, <code>tracert</code>). Cross-platform support is on the roadmap.
</details>

<details>
<summary><b>💬 Where do exported reports go?</b></summary>
<br>
JSON reports are saved in the working directory (or the folder set in <code>report.output_dir</code>) as <code>netx_report_&lt;timestamp&gt;.json</code>.
</details>

<details>
<summary><b>💬 Can I automate NetX (e.g. run it on a schedule)?</b></summary>
<br>
Yes — pair it with Windows Task Scheduler and the report export module to build a lightweight, unattended network health logger.
</details>

<details>
<summary><b>💬 Does NetX send any data externally?</b></summary>
<br>
No. Every module runs entirely on your machine. The only network traffic NetX generates is the diagnostic probes you'd expect — pings, DNS lookups, and traceroutes to hosts you configure.
</details>

<details>
<summary><b>💬 Can I change which DNS resolvers or ping targets are used?</b></summary>
<br>
Yes — edit <code>netx.config.yaml</code> in the project root. See the <a href="#️-configuration">Configuration</a> section for the full list of options.
</details>

<details>
<summary><b>💬 Is NetX safe to use on a corporate network?</b></summary>
<br>
NetX only performs standard diagnostic operations (ping, DNS lookups, traceroute, local adapter reads). As with any network tool, check your organization's acceptable-use policy before running it on managed networks.
</details>
